## Поток данных в пайплайне

Каждая фаза реализует одну и ту же логику пайплайна:

```
1. Получить транзакции
        ↓
2. Обогатить фичами пользователей ──┐
        ↓                           │ (Параллельно в Фазах 2/3)
3. Обогатить риск-скорами мерчантов ┘
        ↓
4. Формирование фичей
        ↓
5. Инференс ML-модели
        ↓
6. Сохранение предсказаний
        ↓
7. Отправка метрик
```

## Архитектуры по фазам

### 1: Crontab

```
┌──────────────┐
│     Cron     │
│  Планировщик │
└──────┬───────┘
       │ Каждые 2 мин
       ▼
┌──────────────┐
│    Python    │
│    Скрипт    │
└──────┬───────┘
       │
       ▼
 [Шаги пайплайна]
```

**Характеристики:**
- Один процесс
- Последовательное выполнение
- Нет встроенных повторов
- Ручная обработка ошибок

### 2: APScheduler + Dramatiq

```
┌──────────────┐      ┌──────────────┐
│ APScheduler  │─────▶│    Redis     │
└──────────────┘      │   (Broker)   │
                      └──────┬───────┘
                             │
                             ▼
                      ┌──────────────┐
                      │   Воркеры    │
                      │  (Пул из N)  │
                      └──────────────┘
                             │
                             ▼
                      [Очередь задач]
                             │
                             ▼
                      [Задачи пайплайна]
```

**Характеристики:**
- Очередь задач
- Параллельные воркеры
- Автоматические повторы с backoff
- Лучшая изоляция

### Фаза 3: Airflow

```
┌──────────────┐      ┌──────────────┐
│   Airflow    │      │  PostgreSQL  │
│ Планировщик  │◀────▶│  (Метаданные)│
└──────┬───────┘      └──────────────┘
       │
       ▼
┌──────────────┐      ┌──────────┐
│   Airflow    │◀────▶│   XCom   │
│  Исполнитель │      └──────────┘
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ Веб-сервер   │
│     (UI)     │
└──────────────┘
       │
       ▼
  [Задачи DAG]
```

**Характеристики:**
- Полноценный workflow движок
- Богатый UI
- Визуализация DAG
- XCom для передачи данных
- Поддержка backfilling

## Данные

### Форматы ответов API

**Транзакции:**
```json
{
  "transaction_id": "tx_12345",
  "user_id": "user_67890",
  "merchant_id": "merch_abcde",
  "amount": 125.50,
  "payment_method": "credit_card",
  "device_type": "mobile",
  "timestamp": "2025-01-25T10:30:00Z"
}
```

**Фичи пользователей:**
```json
{
  "account_age_days": 365,
  "total_transactions": 150,
  "avg_transaction_amount": 87.50,
  "failed_transactions_last_30d": 2,
  "account_status": "verified"
}
```

**Риск мерчанта:**
```json
{
  "risk_score": 0.35,
  "dispute_rate": 0.02,
  "status": "active"
}
```

### Фичи для модели

После feature engineering каждая транзакция превращается в:

```python
[
    amount,                          # Float
    payment_method_encoded,          # 0, 1, 2, 3
    device_type_encoded,             # 0, 1, 2
    hour_of_day,                     # 0-23
    is_weekend,                      # 0 или 1
    account_age_days,                # Integer
    total_transactions,              # Integer
    avg_transaction_amount,          # Float
    failed_transactions_last_30d,    # Integer
    account_verified,                # 0 или 1
    merchant_risk_score,             # 0.0-1.0
    merchant_dispute_rate,           # 0.0-1.0
]
```

### Выход модели

```python
{
    "transaction_id": "tx_12345",
    "fraud_probability": 0.73,       # 0.0-1.0
    "is_fraud": 1                    # 0 или 1 (порог=0.5)
}
```

## Метрики

Отправляются в Prometheus Pushgateway:

- `fraud_rate{participant="имя"}` - (0.0-1.0)
- `transactions_processed_total{participant="имя"}` - Всего обработано транзакций
- `pipeline_duration_seconds{participant="имя"}` - Время выполнения
- `api_failures_total{participant="имя",service="X"}` - Количество ошибок API
- `avg_fraud_probability{participant="имя"}` - Средняя вероятность фрода

## Подставы

### Ожидаемые сбои

1. **API Merchant Risk** намеренно нестабилен
   - Таймауты: ~30% запросов
   - Ошибки 500: ~10% запросов
   - Надо что-то придумать. Как вариант, использовать дефолтные риск-скоры

2. **API пользователей** - Иногда 404
   - Ну типа новые пользователи ещё не в базе
   - Использовать дефолтные фичи пользователей?

3. **API транзакций** - Rate limiting
   - 10 запросов/минута
   - Решение: Не запрашивать слишком часто

### Стратегия обработки

- **Фаза 1:** Ручной try/except везде
- **Фаза 2:** Декораторы retry в Dramatiq
- **Фаза 3:** Конфигурация retry в Airflow
